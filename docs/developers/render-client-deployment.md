# Client-owned Render deployment

This runbook is for setting up the LeadPerfection connector in a Render
workspace owned and operated by Discountbath. The assistant owner can be the
workspace's only member. The developer does not need Render access for normal
code releases because GitHub Actions calls a narrowly scoped Render deploy hook
after the tests for a `main` push pass.

The deployment is defined in the repository's `render.yaml`. It creates:

- one paid, always-on Node.js web service;
- one paid Render Postgres database in the same region;
- generated application encryption/signing secrets;
- private database wiring and the public application URL;
- a `/isAlive` health check; and
- deployment through GitHub Actions only after the complete tests pass.

No AWS account, DynamoDB table, Render API key, shared Render password, or paid
developer workspace membership is needed. One service-specific deploy hook is
stored as an encrypted GitHub Actions secret; it can request a deployment but
cannot read logs, secrets, billing, or database data.

## Before the meeting

### Client/assistant owner prepares

- A business-controlled email address for the Render account.
- A payment card and billing address.
- A phone or authenticator app for two-factor authentication.
- A secure place for recovery codes.
- Permission to enter the four LeadPerfection application settings listed
  below. Do not send the AppKey through ordinary email or chat.
- A decision on the deployment region. `render.yaml` currently selects
  **Virginia (US East)**. Render regions cannot be changed after resource
  creation; changing region later requires new resources and a database
  migration.
- Confirmation that Render's shared outbound IP ranges are acceptable to
  LeadPerfection. If LeadPerfection requires one exclusive static IP, stop
  before purchase because Render requires a more expensive workspace and a
  dedicated-IP add-on for that feature.

Send this question to LeadPerfection support before the meeting if possible:

> For Discountbath's Client ID, are `/token` and API requests restricted by
> source IP? If allowlisting is required, can you accept Render's shared
> Virginia outbound CIDR ranges, or must the integration use one exclusive IP?

Do not include a password or AppKey. If support has not answered by the meeting,
make this the single go/no-go decision before applying the paid Blueprint.

### Developer prepares

- Open the repository's **Actions** tab and enable workflows for this fork.
  GitHub does not run workflows in a new fork until its owner accepts the
  one-time acknowledgement. Then open the **Tests** workflow and choose **Run
  workflow** on `main`; it must pass before the meeting. Because the Render hook
  does not exist yet, the deploy step safely skips.
- Make sure all automated tests pass and the deployment changes are pushed to
  `main` before the meeting.
- Keep the production values below available in a password manager or another
  screen-share-safe source. Never upload the local `.env` file.
- Open this runbook and the public repository URL:
  `https://github.com/efra8ab/lp-connector`.
- Keep one harmless LeadPerfection test user available for the post-deployment
  sign-in and contact lookup. Individual agent passwords are entered by those
  agents in App Connect; they are not Render service variables.

## Values entered during Blueprint creation

Render will prompt for only these secret/client-specific values:

| Variable | Meaning | Source |
|---|---|---|
| `LP_BASE_URL` | LeadPerfection API base URL, without a trailing slash | Existing protected production configuration |
| `LP_CLIENT_ID` | Discountbath's LeadPerfection Client ID | Existing protected production configuration |
| `LP_APPKEY` | LeadPerfection application key | Existing protected production configuration |
| `LP_EMPLOYEE_ID` | Valid fallback employee ID for call logging | Existing validated production configuration |

`APP_SERVER_SECRET_KEY` and `HASH_KEY` are generated by Render. Do not replace
or rotate them casually: they protect persisted credentials, sessions, and
stable hashed identifiers. A rotation needs an explicit migration/reconnect
plan.

Do not add AWS or DynamoDB variables. Do not add `USE_CACHE` or
`USE_TOKEN_REFRESH_LOCK_PLATFORMS` for this deployment.

## Meeting procedure (approximately 30–45 minutes)

1. The assistant owner creates or signs in to the Render account using the
   business-controlled email, enables two-factor authentication, stores the
   recovery codes, and adds the client payment method.
2. Keep the workspace on the single-member **Hobby** plan. Inviting another
   member requires the paid Pro workspace; it is not required for this setup.
3. Open the repository's public
   [Deploy to Render page](https://render.com/deploy?repo=https%3A%2F%2Fgithub.com%2Fefra8ab%2Flp-connector)
   in the assistant owner's signed-in browser. Render reads `render.yaml` from
   `main`; the assistant owner does not need to be a GitHub contributor.
4. Before applying the Blueprint, review both resources:
   - web service `discountbath-lp-connector` on the paid 0.5 CPU / 512 MB plan;
   - Postgres `discountbath-lp-db` on the paid 0.1 CPU / 256 MB plan with 1 GB;
   - both resources in Virginia; and
   - the total estimated monthly amount shown by Render.
5. Enter the four `LP_*` values when Render prompts. Keep secret values hidden
   from recordings and screenshots.
6. Apply the Blueprint and wait for the database and web service to become
   available. The first build can take several minutes.
7. Open the web service URL plus `/isAlive`. Success is an HTTP 200 response
   with `OK`.
8. In the web service's network/outbound view, copy the Virginia shared outbound
   IP ranges into the client's operations record. Send only those ranges—not
   credentials—to LeadPerfection support if allowlisting is needed.
9. In the web service settings, copy its deploy hook directly into the GitHub
   repository secret named `RENDER_DEPLOY_HOOK_URL`. Do this during screen share
   without sending it through chat or email. The service should keep automatic
   deploys **off** because the GitHub test workflow triggers this hook itself.
10. Pushes to `main` now run tests and request deployment of that exact tested
    commit only after they pass. Confirm the GitHub Actions workflow recognizes
    the secret; the actual post-meeting code push will provide the final
    end-to-end proof.
11. Bookmark the web service, database, logs, events, environment, and recovery
    pages for the assistant owner.

## Acceptance checklist before ending the meeting

- [ ] Client business email owns the Render account and workspace.
- [ ] Two-factor authentication, recovery codes, and billing are client-held.
- [ ] The workspace is Hobby with only the assistant owner as member.
- [ ] Web service and Postgres are paid, available, and in the same confirmed
      region.
- [ ] The web service is connected to this public repository and `main` branch.
- [ ] The Blueprint has generated the two application secrets and stored the
      four LeadPerfection settings.
- [ ] `/isAlive` returns HTTP 200 and `OK` from the Render URL.
- [ ] The outbound IP ranges are recorded and the static-IP question is closed.
- [ ] `RENDER_DEPLOY_HOOK_URL` is stored only as an encrypted GitHub secret.
- [ ] GitHub Actions is enabled for this fork and the **Tests** workflow passes
      on `main`.
- [ ] Render automatic deploy is off; the GitHub test workflow triggers the
      hook only after tests pass on `main`.
- [ ] The assistant owner knows where to view logs, redeploy, roll back, and
      access database recovery.

## Working without Render access

Normal developer workflow remains:

```text
developer pushes/merges to main
        ↓
GitHub Actions runs the complete test gate
        ↓ checks pass
Render builds and deploys the commit
        ↓
/isAlive confirms the new service is healthy
```

The developer can continue implementation and release work through GitHub.
The assistant owner is needed only for production-only operations such as
reading full Render logs, changing environment variables, manual rollback,
database export/recovery, billing, or account security. Handle those through a
short screen-share session; never share the Render password, recovery codes,
or personal API keys. Treat the deploy hook like a password: keep it only in
the GitHub secret store and regenerate it in Render immediately if it leaks.

If regular independent production operations become necessary later, upgrade
the workspace to Pro and invite the developer with the least privilege needed.
That is a future operational decision, not a pilot requirement.

If this repository is made private or moved later, reconnect the service using
a Git deployment credential that can read the new repository before the
change, or deployments will stop.

## Post-deployment work (not part of account setup)

After the meeting, the technical validation sequence is:

1. Perform a controlled sign-in and harmless production contact lookup.
2. Exercise an expired-token refresh against the hosted service.
3. Complete one real agent's hosted call-log and notes workflow.
4. Create a Postgres logical export and perform a documented restore test.
5. Run the approved one-agent, one-working-day pilot before wider rollout.

The assistant owner should remain present or available during the first hosted
validation so production logs can be viewed if needed.
